# DotNetFrameworkToolkit Roadmap

| Planning context | Decision |
| --- | --- |
| Review baseline | `master` at [`00a8211`](https://github.com/aaron-salisbury/DotNetFrameworkToolkit/commit/00a8211ce68a7576eac1f7cb315827d3e24e2d0b), reviewed October 1, 2026. |
| Platform | Keep the shipped library on .NET Framework 2.0 / CLR 2.0. Modern C# and modern build tooling remain separate from consumer runtime requirements. |
| Review limits | Source review of library, Cake tasks, package configuration, and GitHub workflow. Existing CI establishes compilation and CLR metadata; it does not establish behavioral or actual CLR 2.0 runtime compatibility. No code, build, or workflow changes were made for this roadmap. |
| Sequencing | Follow phase order by default. Add regression tests alongside later changes; consumer documentation can progress throughout. Phase 7 depends on verified tests, package contents, and consumer installation. |

| Phase | Status | Focus | Review basis | Planned work | Completion criteria |
| --- | --- | --- | --- | --- | --- |
| 0 | Completed foundation | First-pass fixes and build baseline | Result, validation, logging, authentication, file-operation, and DI fixes are merged; Windows Debug/Release builds and CLR metadata checks exist. Unit tests and database TODOs remain. | Retain the current compatibility rules, [development conventions](development_conventions.md) as the baseline. | Merged baseline and compile workflow are available. Completion here does not imply behavioral verification. |
| 1 | In progress | Add unit tests | The tests project targets .NET Framework 4.8.1 and uses MSTest; only the shipped library must target net20. | Run `DotNetFrameworkToolkit.Tests` through Cake and the Visual Studio test runner. Cover results, aggregate exceptions, validation updates/snapshots, Unicode credentials and iteration bounds, logging templates/scopes/retention, filesystem failure preservation, and registration snapshots. Add controlled-barrier concurrency tests and wire test execution/results into Cake and GitHub Actions. | Tests execute rather than merely compile; runner/runtime limitations are explicit; failures are mapped to the relevant hardening phase. Avoid coverage quotas or tests that only mirror implementation. |
| 2 | Planned | Harden DI ownership and shutdown | The public [scope-factory constructor](../src/DotNetFrameworkToolkit/Modules/DependencyInjection/Implementation/ServiceScopeFactoryPNP.cs) creates a root provider without exposing its disposal. Custom Unity lifetime managers and operation draining need behavioral verification against Unity 1.2. | Give directly constructed factories an explicit ownership/disposal contract or remove that construction path. Test supplied-instance ownership, dependency disposal order, singleton resolution through scopes, construction failures, concurrent resolution/disposal, reentrant callbacks, and raw-container wrapping. Clarify repeated/concurrent disposal behavior; fix reproducible defects without promising unrestricted callback reentrancy. | Lifetime tests pass against the pinned Unity package; every supported construction path has a reachable owner; controlled interleavings finish without deadlock or duplicate disposal. |
| 3 | Planned | Reduce the database footprint | The core package directly references and ships a SQL CE dependency. [Initialization](../src/DotNetFrameworkToolkit/Modules/DataAccess/Database/Initialization/SqlServerCEDatabaseInitializer.cs) still discovers migrations across loaded assemblies and has interrupted-creation/lock TODOs; [migration execution](../src/DotNetFrameworkToolkit/Modules/DataAccess/Database/Migrations/SQLServerCEMigration.cs) has cross-process coordination TODOs. | Decide which database contracts genuinely belong in this toolkit. Remove application-specific initialization/migration assumptions and SQL CE from the main package; retain only justified neutral contracts, with an optional database adapter only if a concrete consumer needs it. Document breaking changes. Repair remaining database TODOs only for code intentionally retained. | Installing the main package no longer brings SQL CE/native database requirements. Retained database behavior has explicit ownership and tests; removed assumptions are not replaced with another mandatory database framework. |
| 4 | Planned | Finish public-contract and logging hardening | [Logging scopes](../src/DotNetFrameworkToolkit/Modules/Logging/Implementation/LoggerPNPScope.cs) can be constructed directly, bypassing `BeginScope`'s lifetime check. Scope state is thread-owned, template parsing is custom, and credentials intentionally have no format identifier after the 0.x compatibility break. | Define and test direct scope construction after logger disposal, nested/out-of-order disposal, worker-thread cleanup, duplicate/mixed named and numeric templates, formatting failures, and observer exceptions. Lock down result edge cases, validation notification rules, and credential persistence expectations. Decide whether future credential format changes require versioning; do not reintroduce legacy verification automatically. | Public contract tests pass; scope creation cannot silently bypass the agreed lifetime policy; template/error behavior and stored credential compatibility are documented. Any format change has an explicit migration or reset decision. |
| 5 | Planned | Verify the complete Cake/package pipeline | [CI](../.github/workflows/legacy-framework-build.yml) invokes `Test`, so it does not exercise image generation or NuGet packing. [ICO output](../build/Build/Tasks/ProcessImagesTask.cs) uses `File.OpenWrite`, which can leave trailing bytes when overwriting a larger file. Package version and assembly versions are maintained separately. | Exercise clean Release builds through image generation and `Package`; make image overwrites truncate safely and verify resource disposal and PNG/ICO outputs. Validate `.nupkg`/`.snupkg` contents, dependency metadata, XML/PDB files, and configuration isolation. Make package analysis explicit rather than relying on `NoPackageAnalysis = true`. Establish intentional package/assembly/file version rules and tag validation. | A clean Windows build produces validated package artifacts; a larger-to-smaller ICO overwrite retains no stale bytes; symbols and dependencies are correct; no Debug/intermediate binaries enter the release package. |
| 6 | Planned | Document and verify consumer use | The root README still shows launcher paths without the `build/` directory and offers little guidance for ownership, result semantics, validation, or deployment. CLR metadata alone does not prove a real legacy application can load the packaged library. | Add concise usage examples and migration notes for DI, results, logging scopes, validation, credential persistence, and database removals. Correct build instructions and explain Windows prerequisites. Install the produced package into a minimal net20 consumer and verify runtime loading/representative operations in a suitable Windows CLR 2.0 environment; document shim-name collisions and remaining dependency/native requirements. | Examples compile; the package installs and runs in the declared environment; documentation distinguishes modern compiler/build requirements from legacy runtime requirements and records any unverified platforms. |
| 7 | Planned | Add GitHub release automation for NuGet | A pack task exists, but there is no release/publish workflow. Current CI uploads compilation outputs only. | Add a separate release workflow for an intentional version tag or GitHub release. Reuse Cake's verified Release/package path, require successful tests/package checks, validate the requested version, and publish the validated NuGet package and supported symbols. Prefer NuGet trusted publishing where available; keep any required credentials out of the repository. Attach artifacts and release notes; handle reruns without silently replacing a published version. | A prerelease can be published and installed from NuGet with matching version metadata, usable artifacts, and a traceable source commit. PR/build workflows cannot publish; failed validation prevents publication. |
